# Deploying AURORA to production

This is the checklist for taking the app from `localhost:3000` to a real
URL. Every step here needs an account/action only you can do (Vercel,
Stripe, Neon, Resend, Sentry all require your own credentials) — this is
the guide for doing it, not something that could be automated from this
repo alone.

---

## 1. Push to GitHub

Vercel deploys from a Git repository, not a local folder.

```bash
git init
git add .
git commit -m "Initial commit"
```

Create a repo on GitHub, then:
```bash
git remote add origin https://github.com/YOUR_USERNAME/aurora.git
git push -u origin main
```

## 2. Production database

Don't reuse your local dev database for production traffic. Two good options:

- **Neon branching** (recommended, since you're already on Neon): in the
  Neon console, create a new branch called `production` from your `main`
  branch, or just create a second Neon project dedicated to production.
- A separate Neon project entirely, if you'd rather keep dev and prod
  fully isolated.

Either way, you'll end up with a new `DATABASE_URL`/`DIRECT_URL` pair for
production — **don't reuse the ones from your local `.env`.**

Once you have the production connection string, run the migrations
against it from your machine (one-time, before the first deploy):
```bash
DATABASE_URL="<production-pooled-url>" DIRECT_URL="<production-direct-url>" npx prisma migrate deploy
```
`migrate deploy` (not `migrate dev`) is the non-interactive command meant
for this — it applies existing migrations without prompting or trying to
create new ones.

Seed the production catalog if you want the same demo products live:
```bash
DATABASE_URL="<production-url>" DIRECT_URL="<production-direct-url>" npx prisma db seed
```

## 3. Import the project into Vercel

1. [vercel.com](https://vercel.com) → **Add New → Project** → import your
   GitHub repo. Vercel auto-detects Next.js — no build config needed.
2. Don't deploy yet — add environment variables first (next step), or the
   first build will fail on missing `DATABASE_URL` etc.

## 4. Environment variables (Vercel → Settings → Environment Variables)

| Variable | Production value |
|---|---|
| `DATABASE_URL` / `DIRECT_URL` | The production Neon strings from step 2 |
| `AUTH_SECRET` | A **new** value — generate a fresh one, don't reuse dev's: `openssl rand -base64 32` |
| `NEXTAUTH_URL` | Your real production URL, e.g. `https://aurora-yourname.vercel.app` |
| `NEXT_PUBLIC_SITE_URL` | Same real URL — this feeds metadata, the sitemap, and Stripe's success/cancel URLs |
| `STRIPE_SECRET_KEY` / `NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY` | Live keys if you're taking real payments, or your existing **test** keys if this is still a portfolio demo — see the note below |
| `STRIPE_WEBHOOK_SECRET` | A **new** one — see step 5, this is different from your local `stripe listen` secret |
| `CLOUDINARY_*` | Only needed once real product photography replaces the line-art illustrations |
| `RESEND_API_KEY` / `EMAIL_FROM` | See step 6 |
| `SENTRY_DSN` / `NEXT_PUBLIC_SENTRY_DSN` | See step 7 |
| `SENTRY_ORG` / `SENTRY_PROJECT` / `SENTRY_AUTH_TOKEN` | Optional — only for source map upload |
| `NODE_ENV` | Vercel sets this automatically — don't set it manually |

**Test mode vs. live mode, for a portfolio project:** unless you actually
intend to sell real clothing, keep Stripe in **test mode** even in
production. There's nothing wrong with a live, deployed URL that processes
test-card payments only — that's a completely normal and honest state for
a portfolio piece, and it's one less thing (real money, real refunds,
business verification) to manage.

## 5. Stripe webhook for production

Your local `stripe listen` secret only works for localhost forwarding — it
does nothing in production. You need a **separate, real webhook endpoint**:

1. Stripe Dashboard → Developers → Webhooks → **Add endpoint**.
2. Endpoint URL: `https://your-production-url.com/api/webhooks/stripe`
3. Select the `checkout.session.completed` event (the only one this app
   listens for right now).
4. Copy the **signing secret** shown after creating it — that's your
   production `STRIPE_WEBHOOK_SECRET`.

## 6. Resend — verify a sending domain

Resend's free tier can send from `onboarding@resend.dev` with no setup,
which is fine for testing but will look wrong in a real confirmation
email. To send as `orders@yourdomain.com`:

1. Resend Dashboard → Domains → **Add domain**.
2. Add the DNS records it gives you (SPF, DKIM) at your domain registrar.
3. Once verified, set `EMAIL_FROM="AURORA <orders@yourdomain.com>"`.

If you don't have a domain yet, leaving `RESEND_API_KEY` unset is also
fine — emails will keep logging to Vercel's function logs instead of
sending, same as they log to your terminal locally (see `lib/email.ts`).

## 7. Sentry

1. [sentry.io](https://sentry.io) → create a project → choose Next.js.
2. Copy the DSN into both `SENTRY_DSN` and `NEXT_PUBLIC_SENTRY_DSN`.
3. Optional, for readable stack traces instead of minified bundle
   positions: Settings → Auth Tokens → create one, set `SENTRY_AUTH_TOKEN`,
   `SENTRY_ORG`, and `SENTRY_PROJECT`. Without these three, deploys still
   succeed — source maps just won't upload.

## 8. Deploy

Back in Vercel, click **Deploy**. Once it's live:

- Visit `/sitemap.xml` and `/robots.txt` — confirm they render (both are
  generated dynamically from the database via `app/sitemap.ts`/`robots.ts`).
- Run through the full loop once against production: register → verify
  email → log in → add to bag → checkout with Stripe's test card
  (`4242 4242 4242 4242`) → confirm the webhook fires (Stripe Dashboard →
  Webhooks → your endpoint → recent deliveries) → order shows up under
  `/account/orders`.
- Run Lighthouse (Chrome DevTools → Lighthouse tab) against the deployed
  URL, not localhost — dev-mode Next.js is never representative of
  production performance.

## 9. Custom domain (optional)

Vercel → Project → Settings → Domains → add yours, follow the DNS
instructions. Update `NEXT_PUBLIC_SITE_URL` and `NEXTAUTH_URL` to match
once it's attached, and add a second Stripe webhook endpoint (or just
update the existing one's URL) to point at the new domain.

---

## What this checklist deliberately doesn't cover

- **CI/CD beyond Vercel's own git-push-to-deploy.** A real team project
  would add GitHub Actions running typecheck/lint/tests on every PR before
  Vercel's preview deploy — not set up here, flagged as a next step rather
  than silently skipped.
- **Staging environment.** Vercel's preview deployments (automatic on
  every PR) cover a lot of this already; a fully separate staging DB/env
  is the natural next step for a team, not a solo portfolio project.
- **Database backups/point-in-time recovery.** Neon supports this on paid
  tiers — worth enabling before any real customer data lives in it.
